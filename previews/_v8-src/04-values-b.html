How a check is learned

  1. An agent fails with an environmental signature: ENOSPC, command not found, EADDRINUSE, connection refused.
  2. baton writes a candidate check to the project's env node, with why and when, plus the command that fixed it, if one ran.
  3. The next run checks it before agent 1. A check that never fires for 30 runs is marked dormant and is never silently deleted.

Where it runs

As the first stage of every baton template, in /baton doctor, and on /baton resume. Shell only: no model call, seconds per run.

The unit-loop template is the shape every one of your Workflow scripts rebuilt by hand: a builder, a fresh verifier that never edits, a fix round, a re-verify. It breaks on the first failure, logs its round cap, and spawns a design unit when the same finding comes back.

Inside unit-loop

export const meta = { name: 'unit-loop', phases: [
  {title:'Preflight'}, {title:'Build'}, {title:'Verify'},
  {title:'Fix'}, {title:'Re-verify'} ] }
// args: { units, models, rulings, cap: 3 }
for (const u of args.units) {
  const b = await agent(build(u), {model: args.models.build, schema: BUILD})
  if (!b) break                       // never `continue` past a failure
  let v = await agent(verify(u, b), {model: args.models.verify, schema: FINDINGS})
  for (let r = 1; open(v) && r <= args.cap; r++) {
    if (recurs(v, seen)) { await agent(design(u, v), …); break }
    await agent(fix(u, v), {model: args.models.build})
    v = await agent(verify(u), {model: args.models.verify})  // a new verifier
  }
  log(`${u.id}: rounds=${r} open=${count(v)}`)   // the cap is logged, never silent
}

Merge queue

A unit whose PR waits on you parks in the queue. Units that don't depend on it keep going. When gh shows the merge, the parked unit resumes on its own. "I am not at a place where I can do the merges. Is there nothing else you can complete first?" stops being a question.

How a ruling travels

  1. You say it. A quick filter on keywords (always, never, from now on, don't) decides whether to ask a model. If so, Haiku 5.5 extracts one standing rule, or none.
  2. It becomes a node in the user catalog (everywhere) or the project catalog (this repo). It is newest-first, and it can supersede an older ruling.
  3. The mod writes the active set to .claude/baton/rulings.md (and ~/.claude/baton/rulings.md for user scope), which CLAUDE.md imports.
  4. Every agent loads it: the main session, Agent-tool agents, Workflow agents, and the next session.
  5. Optional enforcement: /baton enforce R-12 turns a ruling into a refusal the mod applies to matching tool calls.

Why a file and not the prompt

For a Workflow agent, a mod can refuse the spawn but not change its prompt or model. Files every agent already loads are the one channel that reaches all of them, and they keep working when the mod isn't installed.

10Watcher, not manager

Scout freely. Get nudged, not blocked.

Why a meter, not a wall

v7 made the prime mechanical: during a run, anything but dispatching, asking and memory was refused. That fights the pattern Claude Workflows are built for, which is to scout inline (list files, read the diff, scope the work) and then orchestrate.

v7's own experiments say what the prime is for: on Opus 5.5 there was no context rot to fix (831K tokens, 29 compactions, same score). A lean prime cost $14.78 vs $20.40. So the value is cost and continuity, and a meter keeps most of the saving without blocking anything.

The rules

  • Counts Bash, Edit and Write in the main thread since the last Agent or Workflow dispatch.
  • Reads and searches never count.
  • Starting thresholds, both tunable: 25 counted calls, or context past 300k.
  • One nudge per stretch: dispatch, close + resume, or keep going.
  • /baton prime turns on v7's strict wall for a session.

Evidence

  • itsjusthtml: 4,557 Bash calls, 10 compactions at about 970k tokens, 5.9B cache-read tokens in the main thread
  • samen: 463 and 381 Bash calls in two sessions, with 0 agents
  • baton v7's own build: 800 Bash calls in the prime
