How the mod sees every Workflow agent

Claude Code tells a mod about every agent a Workflow script starts, and about every tool call those agents make. baton listens to both. It never steers the agents; it only watches, records and shows.

What the mod receives

eventgives baton
agent.spawne.workflow = { runId, agentIndex }: which run, which agent. Fires for every agent() a script starts.
tool.callEach call carries the agent's agentId, so an Edit, a Bash test run or a commit lands in that agent's feed.
wf_*.json + journal.jsonlPhases, labels, state, tokens, and what each agent returned. These files are already written for every run.
agent transcripts.message.model, the model that really served each turn

What it can't do, on purpose

For Workflow agents the mod can only refuse a spawn: their prompt and model can't be rewritten. So guidance travels through files every agent reads (rulings, catalogs) and through templates, never through the mod reaching into a running script.

Why it matters

  • F# Campfire: 29 bare "Status" prompts out of about 100. taal: 8 of 19.
  • Hand-made Monitor watchers on journal.jsonl to learn when a unit finished.
  • "when could I expect the next data point?", "ETA?"
  • No sign that /workflows was ever opened. The view has to come to you.

A graph of small facts, entered through catalogs

v7's memory is a timeline: an append-only log of notes of at most 280 bytes, with a tree of summaries over it. It answers "what happened lately" well and "what do we know about X" badly. v8 keeps the timeline and adds the second axis: things.

Three kinds of node

kindbodyexample
rootone row per catalogMEMORY.md, about 1 KB, always loaded
catalogrows "name: hook → [[link]]", capped near 40; overflow becomes a sub-catalogproject:shop, tech:rust
nodeone fact, links, source + commit, supersedesproject:shop/how-to-test

Rules that keep it healthy

  • Every node is reachable from a catalog. Orphans are flagged.
  • Stale is shown, never hidden. A node whose source has a newer commit says so until someone re-checks it.
  • Agents append notes; a Haiku 5.5 curator folds them into nodes at boundaries. That is v7's merge job, retargeted.
  • Plain Markdown files. Any agent can Read them, with or without the mod.

The session node: continuous, checked, portable

What it holds

fieldfrom
open runsrun ID, script path, the next unfinished agentIndex, any agent in flight
PRs + merge queuegh, at write time
decisions pendingquestions you haven't answered
rulings addedthis session's new rulings, already in the user/project catalogs

Three properties make it bulletproof

  • Continuous. It's rewritten at every agent completion (the watcher sees each one). /baton close is just the final save. A session limit, crash or compaction writes the same row.
  • Checked. Resume re-reads gh, git and the env checks before trusting the row: merged PRs unblock units, moved branches queue a re-baseline.
  • Portable. It lives in the project catalog on a hidden git ref, so another machine can resume.

It fits your handoff habit

/baton close can also write the session-prompt file and print the single line Read @/abs/path and execute. That file's body is "run /baton resume".

Evidence

  • A stop killed a cable-suite agent two-thirds of the way through.
  • taal and onCrack both died on session limits mid-run.
  • "I'm saddened you didn't continue last night": with clear goals, resume continues on its own.

How a check is learned

  1. An agent fails with an environmental signature: ENOSPC, command not found, EADDRINUSE, connection refused.
  2. baton writes a candidate check to the project's env node, with why and when, plus the command that fixed it, if one ran.
  3. The next run checks it before agent 1. A check that never fires for 30 runs is marked dormant and is never silently deleted.

Where it runs

As the first stage of every baton template, in /baton doctor, and on /baton resume. Shell only: no model call, seconds per run.

07Templates

Build. Verify. Fix. Written once.

The unit-loop template is the shape every one of your Workflow scripts rebuilt by hand: a builder, a fresh verifier that never edits, a fix round, a re-verify. It breaks on the first failure, logs its round cap, and spawns a design unit when the same finding comes back.

  • Merge queue: independent units keep going behind an open PR
  • Model map + rulings passed in, with full IDs

Inside unit-loop

export const meta = { name: 'unit-loop', phases: [
  {title:'Preflight'}, {title:'Build'}, {title:'Verify'},
  {title:'Fix'}, {title:'Re-verify'} ] }
// args: { units, models, rulings, cap: 3 }
for (const u of args.units) {
  const b = await agent(build(u), {model: args.models.build, schema: BUILD})
  if (!b) break                       // never `continue` past a failure
  let v = await agent(verify(u, b), {model: args.models.verify, schema: FINDINGS})
  for (let r = 1; open(v) && r <= args.cap; r++) {
    if (recurs(v, seen)) { await agent(design(u, v), …); break }
    await agent(fix(u, v), {model: args.models.build})
    v = await agent(verify(u), {model: args.models.verify})  // a new verifier
  }
  log(`${u.id}: rounds=${r} open=${count(v)}`)   // the cap is logged, never silent
}

What each script re-invented

baton partre-invented as
fresh verifierOpus "adversarial verify, do not modify source" in every phase
rulingsa COMMON block pasted into every script
tiersa per-unit model: in args
ledgerSTATUS.md, spec/reviews/<unit>.md
budgets3 fix rounds; break after run 1 used continue and wasted later units

Merge queue

A unit whose PR waits on you parks in the queue. Units that don't depend on it keep going. When gh shows the merge, the parked unit resumes on its own. "I am not at a place where I can do the merges. Is there nothing else you can complete first?" stops being a question.

How a ruling travels

  1. You say it. A quick filter on keywords (always, never, from now on, don't) decides whether to ask a model. If so, Haiku 5.5 extracts one standing rule, or none.
  2. It becomes a node in the user catalog (everywhere) or the project catalog (this repo). It is newest-first, and it can supersede an older ruling.
  3. The mod writes the active set to .claude/baton/rulings.md (and ~/.claude/baton/rulings.md for user scope), which CLAUDE.md imports.
  4. Every agent loads it: the main session, Agent-tool agents, Workflow agents, and the next session.
  5. Optional enforcement: /baton enforce R-12 turns a ruling into a refusal the mod applies to matching tool calls.

Why a file and not the prompt

For a Workflow agent, a mod can refuse the spawn but not change its prompt or model. Files every agent already loads are the one channel that reaches all of them, and they keep working when the mod isn't installed.

10Watcher, not manager

Scout freely. Get nudged, not blocked.

Workflows want a main session that looks around first and then launches. So v8's prime is a meter: reads and searches are free, and real grunt work in the main thread counts. Past a threshold you get one quiet offer to dispatch, or to close and resume. The strict v7 wall is still there with /baton prime.

4,557Bash calls in one main thread, 10 compactions, 5.9B cache-read tokens. A cost problem, not a quality one. measured
  • Read / Grep / Glob never count: that's scouting
  • Bash / Edit / Write count since the last dispatch
  • One nudge, then quiet. You decide.
Why a meter, not a wall →
10 · Watcher, not managerclose ✕

Why a meter, not a wall

v7 made the prime mechanical: during a run, anything but dispatching, asking and memory was refused. That fights the pattern Claude Workflows are built for, which is to scout inline (list files, read the diff, scope the work) and then orchestrate.

v7's own experiments say what the prime is for: on Opus 5.5 there was no context rot to fix (831K tokens, 29 compactions, same score). A lean prime cost $14.78 vs $20.40. So the value is cost and continuity, and a meter keeps most of the saving without blocking anything.

The rules

  • Counts Bash, Edit and Write in the main thread since the last Agent or Workflow dispatch.
  • Reads and searches never count.
  • Starting thresholds, both tunable: 25 counted calls, or context past 300k.
  • One nudge per stretch: dispatch, close + resume, or keep going.
  • /baton prime turns on v7's strict wall for a session.

Evidence

What still needs proving

v8 is a design. These are the first things a spike must settle before any of it ships:

  1. Is the mods rollout on? On 2026-10-04 it was "served off", and v7's plugin tests have never run live.
  2. Can Workflow agents call the mod's memory tools? If not, they read the catalog files directly, which still works.
  3. Does a CLAUDE.md import written mid-session reach agents that start later? This decides how fresh rulings are.
  4. Is the requested model visible at spawn, before alias resolution? This decides whether models enforce can catch haiku → 4.5.
  5. Is wf_*.json stable? It's an internal format, so the reader must fail loudly ("format changed") rather than draw blanks.

Build order

  1. Model truth: prices, full IDs, served model on every row
  2. Memory graph format, tools and the curator
  3. Migrate the existing memory: copy, A/B on 10 real openers, swap, archive
  4. Project catalog: session + env
  5. Watch pane + change feed
  6. Rulings to every agent + templates + merge queue
  7. UI-check drivers, then the Haiku tier experiment
