Mode: Builder

## Problem Statement

baton ships **28 personas**: 21 in `personas/lenses/`, 7 in `personas/users/`. The 21 lenses
are predominantly **process lenses** — `coverage-truth`, `scope-creep`, `severity-inflation`,
`rung-fit`, `spec-fidelity`. They check *how the work was done*.

A few carry domain tags already (`adversarial-input` → `[security, edge-cases, fuzzing, boundary, robustness]`;
`assistive-tech` → `[accessibility, screen-reader, keyboard-only, a11y]`), so the gap is narrower than
"no domain experts." The domains genuinely absent from all 28: **data modeling, pricing,
docs/IA, brand and typography, legal/licensing, interface motion, i18n, API design,
observability, product discovery.**

luminaryTeam publishes **40** domain experts covering most of those.

`README.md:134-139` claims the two compose via `PERSONAS: builtin + repo:github.com/ckluis/luminaryTeam`.
That path has never been executed, and it collides with baton's own casting security rule.
This design brings the luminaries in-repo instead.

## What Makes This Cool

**A seat filled by a named voice, with phase-specific behavior.** `personas/CONTRACT.md §4.2`
defines the only luminary mechanism as a **seat upgrade** — a named expert *replaces* the
built-in lens in a seat and inherits its phase duties. §4.1's `roster.yaml` example
(`personas/CONTRACT.md:158`) spells out the semantics: `note: "lens seat filled by a named
expert; lens definition still governs the phase duties"`. So the win is not two personas in
one seat. It is that the `coverage-truth` seat, when filled by James Bach, audits coverage
truth *as Bach would* — same subject, sharper method.

**Phase-awareness is the part nobody has.** Every persona system treats a persona as a fixed
point of view. baton already knows a persona behaves differently in PLAN than in VERIFY —
§2.1 has the duty table — but that table is **generic**. Bach in PLAN and Norman in PLAN are
the same behavior with different nouns. Giving each luminary its own per-duty *method* is the
contribution, and it is a persona-format idea that outlives baton.

## A Note On Vocabulary

`personas/CONTRACT.md` §2.1's table columns are **phase | duty | output | rung**: `PLAN`,
`AUDIT`, `CLASH`, `VERIFY` are *phases* (the values of a persona's `phases:` key); "duty" is the
prose describing what to do in one. This design's sections are therefore `## In <PHASE>`.

**This is never `graph.yaml`'s `phase:` field**, which is an integer (`phase: 2`) naming an
execution stage of the run. Two different things, same word, and the design touches only the
first.

**Section references** are `personas/CONTRACT.md` unless prefixed `prompt/`. Both files have
their own §1.1, §2.1, and §4.1-4.3.

## Constraints

- No dependencies, no build step. baton is markdown resolved against `{BATON}`.
- Foreign rosters must keep loading unmodified (§1.1). Changes here must be additive.
- §4.1 caps a **panel** at 3-7. This design enlarges the **roster**, not the panel — see
  Reconciliations below.
- Existing `PERSONAS: builtin` runs must not silently change seating.

## Reconciliations With The Contracts

The review surfaced four places where this design appears to contradict baton's own contracts.
Each is resolved here rather than left to the implementer.

**§4.1 says "Three to seven per panel. Not forty."** That caps how many personas are *seated in
a run*, not how many are available to cast from — §4.1's own `roster.yaml` example shows a
`selected:` list, i.e. casting choosing from a menu. Vendoring 40 enlarges the pool; the 3-7 cap
is unchanged and still binding, and it also permits a mode's Seats table to list more candidates
than one panel seats. **Action:** amend §4.1 to say "per panel, not per roster, and not per Seats
table" so both distinctions are explicit.

**§1.1 says "Adopting a roster must never require rewriting it."** That rule governs *foreign*
rosters loaded via `repo:`/`path:`. It does not forbid baton from authoring its own builtins.
The `repo:` path stays supported and must still be exercised (Success Criterion 5).

**§4.3 says cards are "bound once, spawned many times, identical every time."** Preserved: one
card per persona carrying all its `## In <PHASE>` blocks. Selection happens at read time, not
bind time (see Recommended Approach part 2).

**`casting.md:19-21` says fetch only the files the seats name.** With 68 persona files that
becomes expensive if casting must read each to tag-match. Resolved by a generated manifest
(part 4).

## Findings That Drove The Design

**The phase-default ceiling — the real reason to vendor.** `personas/CONTRACT.md` §1.1 fills a
foreign persona's defaults as `kind: expert`, `phases: [AUDIT, CLASH]`, `rung: 2`. luminaryTeam
files carry only `name` and `domain`, so every one of the 40 lands with exactly those two phases.

Counted across all 8 modes' Seats tables: **15 of 34 seat-phase slots require PLAN, PROBE, or
VERIFY** — `rung-fit`, `feasibility`, `dependency-order`, `scope-creep`, `severity-inflation`,
`equivalence`, and every `kind: user` seat. **No foreign roster shipping only `name` + `domain`
can ever be seated in any of them.** Roughly 44% of the seat surface is structurally closed to
the `repo:` path, and no amount of tag-matching opens it.

Confirmed empirically by the Gate-0 probe: casting fetched Allspaw for `severity-inflation`, then
had to reject him — the seat is VERIFY-only and his defaulted phases are `[AUDIT, CLASH]`.

Vendoring removes the ceiling, because a vendored file sets `phases:` explicitly. This is the
argument the design rests on. It is structural, it is measurable, and unlike the collision below
it does not depend on a judgment call.

**The Protocol collision — probed, and much smaller than believed.** All 40 luminaryTeam files
open with an identical second-person `## Protocol` block, and `prompt/roles/casting.md:56-61`
mandates that outward-addressed prose be reported as a finding and treated as inert.

**Gate-0 result (executed, not predicted):** casting fetched 6 files — one per REVIEW seat, per
its own "fetch only what fills the seats you need" rule — and reported **one** finding, on the
grounds that it is a single recurring authoring pattern rather than six independent injections.
The run continued; the rule is report-and-proceed, not a gate. The probe rated the call **70/30**:
the text is instruction-shaped and matches the rule's own "skip a step" example, but it was
written for luminaryTeam's native orchestrator rather than aimed at baton, and the branch it
describes never fires.

The severity estimate moved four times before this probe (40 → ≤7 → ≤7-or-40 → 1). **One
non-blocking digest line is not a reason to vendor anything.** It is recorded here as a real but
cosmetic defect that vendoring happens to fix, not as a driver. Open Question 5 is closed.

**The ledger cannot measure itself.** `prompt/CONTRACT.md §7` assigns `ts`/`seconds` to "the spawning
layer," which is a language model with no clock; a live `samen-oss-second-pass` run showed
~11 minutes of drift. **This is a separate concern from personas and has been split out to
`docs/designs/ledger-clock.md`.** It is not blocked by this design and should ship first, since
it is smaller. The review also found the fix is *not* "four words": `phase-runner.md:35-38`
appends the row at **dispatch**, when `verdict` and `seconds` do not yet exist, so §7's schema
is already incoherent with its only implementation. That analysis lives in the split doc.

## Proof Run Result — 2026-08-24

Step 3 executed. James Bach ported to `personas/luminaries/james-bach.md` with `## In AUDIT`,
`## In CLASH`, `## In VERIFY` sections and `phases: [AUDIT, CLASH, VERIFY]`. Same persona, same
artifact (baton's own §9 + `verifier.md`), override as the only variable. Control card identical
through `## Signature Challenge`.

**Result: 4 of 6 findings shared both cited path and priority across conditions. SC4 requires
fewer than half. The mechanism did not demonstrate value.**

**Why it failed.** The `## In AUDIT` override said "state the mutation you mentally applied and
whether the suite would have gone red." Bach's base card already closes with a `## Signature
Challenge` reading *"If this test suite passed on a build where the core feature was completely
broken — would anyone know before a user did?"* — the same test, in the persona's own voice. The
override restated the card instead of extending it, so it carried no information and changed no
findings.

It did shift severity: run A escalated the per-criterion gap to P0 + red flag; the control rated
the same substance P2. Real, but that is a ranking change, not a behavior change, and SC4 does not
measure ranking.

**What this means for the design.** Open Question 1's filter was wrong. "A luminary earns
overrides when its method differs from the generic duty" should read **"…differs from what its own
base card already implies."** A well-authored persona already determines its method through
`## Focus`, `## Style`, and `## Signature Challenge`. The open question is now sharper and harder:
**what fraction of 40 well-written personas can a phase override actually help?** If the answer is
"few", the override mechanism is not worth its contract surface and the vendoring case rests
entirely on the phase-default ceiling (§1.1a) — which is still real, still measurable, and does
not need overrides at all.

**Retry design, before any port resumes.** Author an override that says something the base card
cannot: a phase where the persona's *generic* duty and its *own* instincts genuinely diverge.
`## In CLASH` is the better candidate — the base card lists Conflict Vectors (who it fights) but
never how it concedes, and §2.1's CLASH duty demands a steelman the card says nothing about.
Re-run the A/B there before spending anything else.

**Second proof, at CLASH — also failed.** CLASH was chosen deliberately as the most favorable
remaining phase: base cards list `## Conflict Vectors` (who a persona fights) but never how it
concedes, and §2.1's CLASH duty demands a steelman no card mentions. It converged anyway —
**67% of A's moves and 62% of B's shared both claim and cited path**, against SC4's fewer-than-half
bar. Of the override's three instructions, one restated the base card's `## Signature Challenge`
(the identical failure mode as AUDIT), one was stylistic, and the one with real content — name a
falsifiable withdrawal experiment — was reached by the control on its own, unprompted.

**Disposition: the override mechanism is cut.** Two proofs, on the two phases judged most likely
to diverge, both failed for the same reason: a well-authored persona already encodes its method in
`## Focus`, `## Style`, and `## Signature Challenge`, leaving a phase override nothing to add that
is not restatement. There is no remaining evidence that good personas under-specify their own
method, and a third proof at VERIFY is unlikely to reverse a pattern this consistent.

**What survives, and it is enough.** Vendoring is justified by two structural ceilings, neither of
which needs overrides:

1. **§1.1a phase ceiling** — foreign personas default to `[AUDIT, CLASH]`, locking them out of
   15 of 34 seat-phase slots.
2. **§1.1b tag ceiling** — §4.2 upgrades on a literal `tags` match and `tags` has no default. None
   of luminaryTeam's 40 files carries one, so by contract they can match no hint at all. Casting
   improvises a `domain`-based match, which is why the Gate-0 probe appeared to work; that
   behavior is unspecified and unauditable.

Both are removed by vendoring files that set `phases` and `tags` explicitly. That is now the whole
case, and it is stronger than the one the design started with.

`wf-clash-A-with-override.md`, `wf-clash-B-control.md`, `wf-4-clash-ruling.md`.

## Approaches Considered

Three were offered; all three were rejected in favor of a reframe. One line each:

- **A: Overlay Adapter** — allowlist known-structural sections, ship a `luminaryTeam.md` adapter.
  Rejected: patches rather than removes, and creates a per-roster maintenance tail. *(Worth
  re-weighing now that severity is ≤7 findings, not 40 — noted in Open Question 5.)*
- **B: Roster Standard** — a versioned spec plus conformance validator. Rejected as premature:
  one implementation and one conforming roster is a spec, not an ecosystem.
- **C: Prove It By Running It** — run REVIEW against luminaryTeam and publish the findings as
  the demo. Rejected as the primary path; its core move survives as Next Steps step 0.

## Recommended Approach

**Vendor all 40 luminaries into baton, authored to baton's schema, phase-aware where phase
behavior genuinely differs.** Four parts.

**1. Port all 40 — a mechanical transform, not a rewrite.** Every luminary file already carries
`name` + `domain` frontmatter and baton's five expert sections (`## Focus`, `## Style`,
`## Conflict Vectors`, `## Red Flag Trigger`, `## Signature Challenge`) in baton's order. The
port is: add `kind`, `phases`, `rung`, `tags` to frontmatter; delete `## Protocol` and
`## Audit Output` (baton's role prompts already supply both, which is exactly why they read as
orchestrator-addressed). **The prose transfers verbatim.** The only real authoring work is part 2.

`phases` must be set explicitly on every port — the default is `[AUDIT, CLASH]`, so a file with
`## In PLAN` but no `PLAN` in `phases` would be silently inert.

**2. Add optional per-duty override sections.**

```markdown
## In AUDIT
Read the assertion, never the test name and never the coverage number. For
each finding, state the mutation you mentally applied to the code under test
and whether this suite would have caught it. A finding with no named mutation
is an opinion, not a finding.
```

That is a *method* override: it still audits the artifact the seat was given, judged by the seat's
own lens. It changes how the seat looks, not what it looks at. An override reading "attack the
test strategy in the graph, not the code" would be a *subject* change and is rejected.

Rules, all binding:

- **A persona omitting `## In <PHASE>` inherits §2.1's generic duty.** Overrides are additive,
  so a file carrying only `name` and `domain` still loads. §1.1 is preserved.
- **An override refines *method* only.** The §2.1 row's duty, output shape, and rung columns
  are not overridable and always govern. An override may not change *what* is examined —
  §4.2's "the mode owns what gets examined; the persona owns how."
- **Valid `<PHASE>` for `kind: expert`:** PLAN, AUDIT, CLASH, VERIFY, EXECUTE. For `kind: user`:
  PLAN, PROBE, VERIFY, CLASH.
- **`## In SYNTH` is invalid for both kinds** and casting rejects the file. §2.1 and §2.2 both
  make SYNTH duty "Nothing" as a neutrality invariant; an override there would let a vendored
  file lobby its own findings into the matrix.
- **An `## In <PHASE>` for a duty absent from `phases:` is a validation error** casting reports,
  not silently ignores.
- **A duty valid for the other `kind` is a validation error too** — `## In AUDIT` on a
  `kind: user` file, `## In PROBE` on a `kind: expert` file.
- **`<PHASE>` must match an enumerated duty token exactly** (uppercase, from the sets above).
  A heading like `## In Practice` is ordinary prose and is never treated as an override. This
  is what keeps a foreign roster from acquiring binding overrides by coincidence.
- **Foreign-roster overrides are honored deliberately.** A `repo:` persona carrying a valid
  `## In AUDIT` gets that behavior — richer rosters are a feature, not a leak. Success
  Criterion 6 tests that a file with *no* `## In` headings is unaffected.

**What "validation error" means operationally.** Casting does not halt the run. It records the
file, the offending heading, and the reason in `cast/roster.yaml` under a new `rejected_overrides:`
key, reports them in its digest, and seats the persona with its generic §2.1/§2.2 duties. The
operator sees the list at the cast gate. This mirrors `casting.md:56-61`'s existing posture for
foreign-file findings: report, continue, never silently ignore and never stop.

**3. Name the duty in the spawning role — no schema change required.**

The problem is real: an agent holding a card with four `## In` blocks must know which applies.
`graph.yaml` carries `phase: 2` (an **integer**), and `prompt/CONTRACT.md` §11's footer carries `{rung}`, `{model}`,
`{effort}`, `{work_dir}`, `{handoff_path}`, `{contract_locator}`, `{escalation_path}`,
`{status_path}`, `{digest_path}` — no duty name.

**The duty is a property of the role that spawns the persona, not of the node.** Every dispatch
path already knows its own duty and says so in prose:

| spawner | duty | evidence |
|---|---|---|
| `panel.md` step 1 (audit fanout) | AUDIT | `panel.md:30` — *"This is each seat's AUDIT duty (personas CONTRACT §2.1)"* |
| `panel.md` step 4 (steelman clash) | CLASH | `panel.md:50` — *"Steelman clash"* |
| `panel.md` step 6 (synthesis) | SYNTH — seats silent | `panel.md:66` — *"silent at SYNTH (personas CONTRACT §2.1/§2.2)"* |
| `journey-probe.md` | PROBE | `journey-probe.md:3` — *"`kind: user` persona … spawned by phase runner (or PRIME in PROBE)"* |
| `verifier.md` | VERIFY (`kind: expert`) | the role is the verification duty; spawned by `phase-runner.md` step 5 |

**Gap — `kind: user` VERIFY has no executor.** §2.2 gives user personas a VERIFY duty
("re-drive a claimed fix as this person"), but `verifier.md` never mentions `user`, and
`phase-runner.md` step 5 spawns `verifier.md` generically. Nothing routes a user persona to its
own VERIFY duty. This predates the design; `## In VERIFY` on a `kind: user` file would be inert
until it is resolved. Tracked as Open Question 6.

**Chosen mechanism:** each of these role prompts states the duty in the per-seat spawn text it
already composes. The agent selects its `## In <PHASE>` block from the card it already holds.

This costs **no change to `graph.yaml`, no change to `prompt/CONTRACT.md` §11's footer, and no change to §4.3** —
the card stays single and identical, selection happens at read time. It is a one-line addition
to four role prompts.

*Rejected alternatives, both from an earlier revision of this design:*
- *Phase runner writes `DUTY:` into the handoff.* **Impossible.** `planner.md:18` and `:67` show
  the **planner** writes `handoff.md` for every node, at plan time; `phase-runner.md` contains no
  reference to handoffs at all. Worse, `panel.md`'s slots are `{artifact_path}`, `{roster_path}`,
  `{seats}` — the dominant persona dispatch path carries no handoff to write into.
- *Add `duty:` to the graph node schema and `prompt/CONTRACT.md` §11's footer.* Changes two contract schemas, and
  the footer is appended verbatim to every spawn including non-persona nodes where the field is
  meaningless.

**4. Ship a generated `personas/index.yaml` manifest.** One file listing every builtin persona's
slug, kind, domain, tags, and phases. Casting tag-matches against the manifest in one fetch
instead of reading 68 files, which honors `casting.md:19-21` at the enlarged roster size and
resolves the casting-cost question.

**5. Make the roster reachable — extend the modes.** Review found only ~12-15 of the 40 are
seatable by any mode today, and that the domains the Problem Statement cites (typography, i18n,
motion, docs/IA, API design) are largely the unseatable ones. Rather than shrink the port, widen
the modes. Two tiers:

*Tier 1 — extend upgrade-hint vocabulary (cheap).* Every mode already carries a hints paragraph
(`REVIEW.md:157-162`, `BUILD.md:149`, `IMPROVE.md:148`, `GENERIC.md:100`) naming tags like
`distributed`, `operations`, `economics`, `first-principles`, `ethnography`, `release-engineering`
— **tags no built-in lens carries.** `personas/CONTRACT.md:168-171` says so outright: "With
`PERSONAS: builtin` every hint misses." The modes were built for a roster like this one. Adding
luminary-matching tags to existing hints costs one line per mode and seats every luminary whose
domain fits an existing seat's *subject*.

*Tier 2 — new seats for subjects no seat examines (real work).* An upgrade fills a seat and the
seat's subject still governs (§4.2), so Butterick cannot audit typography unless some seat
examines typography. Domains needing a new seat: brand/typography, i18n, interface motion,
docs/IA, UX copy. **§4.1 caps the *selected panel* at 3-7, not the Seats table** — the `roster.yaml`
example shows casting choosing from a menu — so a mode may list more candidate seats than any one
panel uses. Home these on the UI-surface modes (DOGFOOD, REVIEW) or a new mode.

**6. Preserve the current default.** Vendoring makes upgrade hints that previously *missed*
start to *hit* — every existing `PERSONAS: builtin` run would silently seat different personas.
`builtin` keeps today's 28; luminaries require `builtin+luminaries` (or `roster:luminaries`) to
opt in. Recorded at the top of the CHANGELOG either way.

## Open Questions

1. **BLOCKING, and now the central question.** The filter was wrong: an override must differ
   from **the persona's own base card**, not from the generic duty. Bach's `## In AUDIT` restated
   his own `## Signature Challenge` and changed nothing. Open: **what fraction of 40 well-written
   personas can an override actually help?** If the answer is "few", the override mechanism is not
   worth its contract surface and the vendoring case rests entirely on §1.1a's phase ceiling —
   which stands on its own.
2. **CLOSED — the spawner names the phase and it works.** Implemented in `panel.md` (AUDIT at
   step 1, CLASH at step 4), `journey-probe.md` (PROBE), and `phase-runner.md` (VERIFY on the
   bound-card path). Proof run A confirmed an agent given `PHASE: AUDIT` reads and applies its
   card's `## In AUDIT` section. The *mechanism* works; what failed was the override's *content*
   (see Proof Run Result).
3. **CLOSED — `personas/luminaries/`.** Forced by the source distinction: luminaries in
   `lenses/` would be indistinguishable from process lenses, so `builtin` would silently include
   them. `bundle.sh` now searches `personas/{lenses,luminaries}` and **exits 1** on a missing
   seat (verified: a ghost seat fails the build; all 8 modes still bundle clean).
4. **Canonical source on drift.** luminaryTeam stays published; baton carries a duty-aware set.
   Proposal: different artifacts (standalone advisory panel vs. duty-aware orchestration roster),
   stated in both READMEs. Owner: step 6.
5. **CLOSED by the Gate-0 probe.** Actual severity is one non-blocking finding, 70/30 call. The
   collision no longer justifies anything; the phase-default ceiling does. Approach A (overlay
   adapter) was re-weighed against the corrected severity and is now clearly *insufficient* —
   an adapter cannot widen a foreign persona's `phases`, so it leaves 44% of seats closed.
6. **`kind: user` VERIFY has no executor.** §2.2 defines the duty; `verifier.md` never mentions
   `user` and `phase-runner.md` step 5 spawns the verifier generically. Predates this design, but
   `## In VERIFY` on a user persona is inert until resolved. Owner: step 2.
7. **Real-person naming posture.** Shipping 40 named living individuals' simulated judgment inside
   an MIT tool differs from a standalone advisory panel. **Gates step 5** — resolve and record here
   before porting beyond the proof.

## Success Criteria

1. `PERSONAS: none` still works for every mode; every seat remains fillable by a built-in lens.
2. A `PERSONAS: builtin` REVIEW run before and after the port seats **identical** personas.
   Any change is a regression, not a feature.
3. A `PERSONAS: builtin+luminaries` REVIEW run upgrades at least one seat to a luminary, and its
   findings diverge from the same seat's lens-filled run — **divergence defined mechanically as: fewer
   than half the findings in either run share a cited artifact path AND a priority (P0-P3) with a
   finding in the other.**
4. A luminary with `## In AUDIT` produces observably different AUDIT findings than the same
   luminary without it — same seat, same artifact, override the only variable. This is the only
   test that proves part 2 works, and it uses AUDIT rather than VERIFY to match step 3's proof
   run and to stay clear of the `kind: user` VERIFY gap (Open Question 6).
5. The `repo:` path is exercised once against luminaryTeam so `README.md:134-139` stops being an
   unverified claim.
6. A foreign roster carrying only `name`/`domain` still loads unmodified (§1.1 regression).

## Distribution Plan

Existing pipeline covers it. baton is markdown resolved against `{BATON}` — a base URL or a local
clone; personas ship in-repo and are fetched like everything else.

**The version-pin story needs one action first.** `prompt/baton.md` §2.1 correctly describes the
base URL doubling as a version pin, but `git tag` returns **nothing** — no tag has ever been cut,
so "point at `/v2.0` instead of `/main`" currently resolves to a 404. **Tag `v2.0` at the
pre-luminary commit before merging any of this**, or the pin claim stays false and existing users
have no way to stay on the 28-persona roster.

`./bundle.sh <MODE>` does not grow, since it emits only the seats a mode names. `./bundle.sh` with
no argument (`mode=ALL`) emits every persona file and **does** grow by 40. Consider excluding
luminaries from ALL unless seated.
