D18 · How much of baton should live on GitHub?

You said: "wasn't the concept that this plugin is about more than local work, including issues and tasks? I'm not sold that's necessary given how much can be done today, but that was the concept."

The v5 design notes already pulled back once: putting run state into Issues "so it scales to many people" was measured, and one run wrote about 3,500 state rows, so v5 kept state in git and used Issues only for questions.

What exists without baton today

  • Remote Control answers a session from your phone (the /rc in your session header).
  • PR notifications: a session can subscribe to a PR and gets its reviews, comments and CI as notifications.
  • Routines run scheduled cloud agents on a cron.
  • /code-review reviews a branch or PR, locally or in the cloud.

What D9 already gives you

Committed .baton/ means the catalogs and durable memory travel through git to any machine and any agent, with no issues needed.

D18 · the options

Files first; GitHub as an adapter, and how much of one

1ChosenLocal-first; PRs on, issues opt-inThe core is files. The PR adapter stays on, because every change you ship is a PR and approving from a PR comment works from anywhere. Issues as goals, labels, boards and TEAM: github become an opt-in adapter: kept, tested, not grown in v8.
2GitHub-native stays coreIssue → PR → board by default, Issues as the human lane. Best for teams with a backlog; more setup, more state on GitHub, and it ties baton to one forge, which works against universal-first.
3Local onlyDrop the GitHub features from v8 and lean on Claude Code's own PR notifications, Remote Control and gh. Least to maintain; loses the merge-ready view and remote /approve, and Codex users get no PR view at all.

Why option 1

  • It matches how you work: one operator, every change a PR, you merge.
  • It keeps "more than local": committed .baton/ plus PRs carry the work beyond one laptop.
  • It stays universal: the PR adapter is plain gh, so Codex can use it too; issues and boards are GitHub-only.
  • Nothing is thrown away: the issue flow keeps its 26-check smoke test and turns on with one setting.

What would change my mind

If you expect other people to run baton on shared repos soon, option 2 earns its setup.
