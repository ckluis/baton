Round 5 · guardrails · the theory of constraints · D16, D17

Your review is the constraint; anything a machine can catch never reaches it

With agents writing the code, the bottleneck is your attention for review and verification. Strict checks narrow what an agent can do, so it converges faster, and they move every mechanical catch off your desk. The project catalog's guardrails node lists each rule, what enforces it, and the proof that it fails.

rule (example)enforced byproof it fails
Every PR targets maina CI check on the PR's base brancha test PR opened against a feature branch is refused
Never push to mainbranch protection, plus a mod deny on git push … mainthe denied call appears in the ledger
Build outputs share one target directorythe env preflightpreflight fails on a checkout with its own target directory

Enforce at the highest level that works: architecture (one owner, one supported way) → types → a lint whose error names the fix → a test → a written rule last, because nothing fails when an agent skips a doc.

Close the exits

  • Lint config and CI files are off limits to building agents. The mod denies the edit in Claude; a CI diff check catches it everywhere else.
  • Suppressions need a reason and an expiry. The count goes on the meter; a rising count is the signal.
  • Builders don't edit the tests they're graded against (D17). The mod knows which Workflow agent made each call, so it can enforce paths per role.

Tighten gradually (D16)

  • Record today's violations as a baseline, fail only new ones, and let the count only go down.
  • A rule earns its place after a mistake happens twice. The curator proposes "this ruling came up 3 times, make it a check."
  • Every check is proven to fail once, on purpose, before it counts.
  • Prototypes and press-release spikes run loose.

Measure it

Most of the case for strict linting with agents is practitioner reports. The ledger counts repeat corrections per project before and after each rule lands.

Round 3 · the memory design

A graph of small memories, entered through catalogs

Every memory is a node: one fact, a few hundred bytes to a couple of KB, with [[links]] to other nodes. A catalog is also a node, but its body is only rows of the form "name: one-line hook → link". An agent loads the root, follows one or two catalog rows, and reads only the nodes it lands on.

catalogloaded whenholds rows for
root (MEMORY.md)always (Claude Code already loads it)one row per catalog
useralways (small)how you work: decision tables, PRs to main, never push after handoff, cheap models for fan-outs
project: <repo>cwd is inside itsession (close/resume), env (preflight), how to test, rulings, open PRs, ADR state
tech: <stack>a marker file is present (Cargo.toml, mix.exs, *.fsproj, go.mod)cross-project lessons for that stack
tool: <tool>doctor finds it installedcmux, Claude Workflows, mods, gh: recipes and gotchas, plus the plugin skill to load

Rules for a healthy graph

  • One fact per node. A log becomes a short "current state" node plus dated history nodes linked by previous.
  • Every node is reachable from a catalog. An orphan is flagged, never silently kept.
  • Every node cites its source (path + commit or modified time) and is marked stale when the source is newer.
  • Newest wins through a supersedes link, not by editing history away.
  • Catalog rows are capped (around 40). Overflow becomes a sub-catalog.
  • Agents add notes; a Haiku 5.5 curator folds them into nodes at boundaries. That is today's merge job, retargeted.

Token target

  • Today: MEMORY.md is 13.9 KB (≈3.5k tokens), loaded in every session, and mostly about other projects.
  • Target: root + user + one project + its techs ≈ 4–6 KB, all relevant; anything deeper is read on demand.

P9 · round 2 · settled: the project catalog's env node

Preflight: a 20-second environment check before a long run

Several runs failed hours in for reasons that had nothing to do with the code: the disk filled, a toolchain wasn't on PATH, a database or the Docker VM wasn't up, or a stale dev server held the port. Each failure cost an agent's work and a resume. A preflight checks those once, before the first agent starts, and stops with a clear message instead.

The useful part is that it learns. When a run fails on something environmental (ENOSPC, command not found, EADDRINUSE), baton adds that check to the project catalog's env node. Next run, it's checked up front.
