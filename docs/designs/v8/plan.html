Round 3 · the memory design

A graph of small memories, entered through catalogs

Every memory is a node: one fact, a few hundred bytes to a couple of KB, with [[links]] to other nodes. A catalog is also a node, but its body is only rows of the form "name: one-line hook → link". An agent loads the root, follows one or two catalog rows, and reads only the nodes it lands on.

catalogloaded whenholds rows for
root (MEMORY.md)always (Claude Code already loads it)one row per catalog
useralways (small)how you work: decision tables, PRs to main, never push after handoff, cheap models for fan-outs
project: <repo>cwd is inside itsession (close/resume), env (preflight), how to test, rulings, open PRs, ADR state
tech: <stack>a marker file is present (Cargo.toml, mix.exs, *.fsproj, go.mod)cross-project lessons for that stack
tool: <tool>doctor finds it installedcmux, Claude Workflows, mods, gh: recipes and gotchas, plus the plugin skill to load

Rules for a healthy graph

  • One fact per node. A log becomes a short "current state" node plus dated history nodes linked by previous.
  • Every node is reachable from a catalog. An orphan is flagged, never silently kept.
  • Every node cites its source (path + commit or modified time) and is marked stale when the source is newer.
  • Newest wins through a supersedes link, not by editing history away.
  • Catalog rows are capped (around 40). Overflow becomes a sub-catalog.
  • Agents add notes; a Haiku 5.5 curator folds them into nodes at boundaries. That is today's merge job, retargeted.

Token target

  • Today: MEMORY.md is 13.9 KB (≈3.5k tokens), loaded in every session, and mostly about other projects.
  • Target: root + user + one project + its techs ≈ 4–6 KB, all relevant; anything deeper is read on demand.

P2 · round 2 · settled in round 3 as option 1

Keep the prime, but make it a meter by default, not a wall

Your worry is right. Workflows assume a hybrid main session: scout inline first (list files, read the diff, scope the work), then launch the script. v7's guard refuses every non-dispatch tool during a run, which would block the scouting.

The prime still pays: the itsjusthtml main thread burned 5.9B cache-read tokens over 10 compactions doing grunt work. That's a cost problem, not a quality one (v7 measured no rot on Opus 5.5). So the default should watch cost and suggest, and refuse only when you ask it to.

1.Meter + nudge; wall opt-inRecommendedThe band counts main-thread work since the last dispatch (tool calls, context size). Past a threshold it offers "dispatch this?" or "close + resume". /baton prime turns the v7 wall on for a session.
2.Wall by defaultv7's behavior. It stays lean, but it fights the scout-then-orchestrate pattern and plain chat.
3.No prime conceptDrop it; rely on Workflows and memory alone.

Evidence

  • itsjusthtml: 4,557 Bash calls in the main thread, 10 compactions at about 970k tokens
  • samen: 463 and 381 Bash calls in two sessions, with 0 agents
  • baton v7's own build: 800 Bash calls in the prime
  • v7 E1b: a lean prime cost $14.78 against $20.40 for one carrying 831K tokens, at the same score

Starting thresholds (tunable)

  • Nudge after 25 tool calls since the last dispatch, or when context passes 300k.
  • Never nudge on Read/Grep-only stretches (that's scouting).
P6 · "doesn't our memory resolve this?" · D8

In design yes; in practice it never reached the agents doing the work

v7 already lifts standing rules out of your prompts, keeps the newest, leads every wake with them, and can enforce one as a refusal. Four gaps kept that from helping in the sessions I read:

  1. The mod never ran live. The rollout switch was off, so no session had rulings.
  2. Scope. Rulings live in project memory, but the rules you repeat cross projects (decision-table shape, decisions are issues, cheap models, cmux screenshots). Those survive today only because Claude's own MEMORY.md carries them.
  3. Reach. Rulings lead the prime's wake. Workflow agents can't be prompt-injected (the "mod can watch" slide), and each script re-pasted a COMMON block by hand.
  4. Agents don't know they exist. Lessons are injected at spawn for Agent-tool agents only.
1.Generated rules file + pinned agent typesRecommendedThe mod writes active rulings to a generated .claude/baton/rulings.md, imported by CLAUDE.md, which every agent (Workflow agents included) loads. Templates use baton agentTypes with full model IDs.
2.Template args onlyThe template passes rulings in args as the COMMON block. This works only for baton templates, not hand-written scripts.
3.Prime wake onlyLeave it as v7; agents learn rules only through the prompts the prime writes.

Trade-off in option 1

  • It adds one @.claude/baton/rulings.md line to the project's CLAUDE.md, visible and reviewable, and gitignored if you like.
  • The file still works without the mod: it's just a file.
  • It depends on the step-0 spike (whether a mid-session change reaches agents started later).

P9 · round 2 · settled: the project catalog's env node

Preflight: a 20-second environment check before a long run

Several runs failed hours in for reasons that had nothing to do with the code: the disk filled, a toolchain wasn't on PATH, a database or the Docker VM wasn't up, or a stale dev server held the port. Each failure cost an agent's work and a resume. A preflight checks those once, before the first agent starts, and stops with a clear message instead.

The useful part is that it learns. When a run fails on something environmental (ENOSPC, command not found, EADDRINUSE), baton adds that check to the project catalog's env node. Next run, it's checked up front.

2.Static checklistChecks you write by hand per project.
3.Drop itHandle environment failures when they happen.

Cost

  • Each check is a shell command, so there's no model call, and it adds seconds per run.
  • A learned check is a single note row: check: df -g . | awk … ≥ 20, plus why it was added and when.

Universal

Nothing here is macOS-specific. Checks are plain commands per project, and the shipped defaults are only "disk" and "git clean".

Order of work (round 3)

A spike, then memory first, because everything else hangs off it

  1. Spike (findings note, no PR). Is the mods rollout on? Can Workflow agents call the mod's memory tools? Is agent.spawn with e.workflow and tool.call attribution seen live? Does a CLAUDE.md import reach agents started later?
  2. Model truth (D1, P8). Price rows for Sonnet 5.5 and Haiku 5.5 (Haiku priced per request on prompt size); MECH → claude-haiku-5-5; full IDs; doctor shows alias resolution; the served model ID next to every agent name. Small, and safe to ship first.
  3. Memory graph format + tools. Node and catalog file format, links, supersedes, stale marking, the orphan check, cwd/marker-file catalog selection, the Haiku curator. A CLI that works without the mod (baton mem …), plus the mod's memory tools on top.
  4. Migrate your memory (D10, D11). Built in a copy; A/B on 10 real session openers; swap; archive the originals; the CLAUDE.md rule against root re-flattening.
  5. Project catalog: session + env (P7, P9, D9). Continuous session writes, /baton close, /baton resume with drift checks, learned preflight.
  6. Watcher pane (D3, P1). Run tree from spawn events + wf_*.json; a live per-agent "what changed" feed; Enter drills in; changes also land in the graph.
  7. Rulings reach every agent (D8) + templates (P3, P5). unit-loop, the merge queue, pinned agent types.
  8. UI-check drivers (P4) and the Haiku experiment (D1). The cmux driver first; the experiment needs a budget from you.

Why memory moved ahead of the pane

  • It works without the mod, so it can't be blocked by the rollout switch.
  • Session and env, rulings, tool recipes and the change feed are all writes into the graph. Build the graph once and they become small.

How it's built

  • Sonnet builders, an Opus verifier, one subagent at a time; the hooks module stays one register.js.
  • Your live memory folder is only touched at step 4, after the A/B, and with the originals archived.
