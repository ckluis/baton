# Design: The Ledger Has To Read A Clock

Generated by /office-hours on 2026-08-24 (split from stage-aware-luminaries.md after review)
Branch: main
Repo: ckluis/baton
Status: DRAFT
Mode: Builder

## Problem Statement

`prompt/CONTRACT.md §7` defines the ledger as one append-only row per spawn:

```csv
ts,node,rung,model,effort,attempt,verdict,seconds,note
```

written by **"the spawning layer."** The spawning layer is a language model. It has no clock
and no token counter. It cannot report `ts` or `seconds` except by estimating them.

Observed in the live `samen-oss-second-pass` run: `ledger.csv` timestamps ran **~11 minutes
ahead of wall clock**, ascending plausibly, entirely fabricated. Nothing in the run detected it.

**Direct evidence, from that run's own ledger (30 rows, 2026-08-24):**

```
rows 2-9    :28 :28 :05 :55 :59 :50 :13 :50      irregular — measured
rows 10-18  :00 :00 :00 :00 :00 :00 :00 :00 :00  nine consecutive, all on the minute
row 19      14:32:09  (P2 again, EARLIER than row 18, duplicate node id)
rows 20-31  :42 :38 :36 :36 :25 :50 :27 :34 ...  irregular — measured
```

Nine consecutive rows landing exactly on `:00` is not rounding: at 1/60 per row that is
1 in 60^9. It is one phase runner typing plausible times from memory for a whole band of the
run, while the bands on either side were written by actors that had real values. Row 19 is the
same node id as row 18 with an earlier timestamp, appended after it — an append-only ledger that
went backwards.

**Nobody noticed until a verifier was asked to check a criterion about it.** That is the whole
argument for §7.1 in one artifact.

§7 closes with the line that makes this matter:

> **A run that does not measure where it spent its rungs will spend them the same way next time.**

The rung histogram in `final/report.md` is built from these rows, and §7 says that histogram
"is the input to the next run's entry-rung assignments." A fabricated histogram is worse than
no histogram: it looks like evidence.

## The Deeper Defect

The initial framing of this fix — "four words in §7, tell it to use `date -u`" — is wrong, and
adversarial review caught why.

`prompt/roles/phase-runner.md:35-38` appends the ledger row at **dispatch**:

> Spawn one node orchestrator … Append a ledger row on every spawn (CONTRACT §7 schema).

At dispatch, `verdict` does not exist (the child hasn't run) and `seconds` does not exist (no
elapsed time yet). So §7's schema is **already incoherent with its only implementation**,
independent of the clock problem. A `date -u` at append time would stamp the start, not the span,
and `verdict` would still be a guess about the future.

There is also no store for a start time. §6 enumerates every run-state file; none holds one. A
phase runner respawned mid-phase after a session limit has lost any in-memory start time, which
matters because resume-from-disk is a load-bearing property of the whole design.

## Premises

1. An LLM cannot measure elapsed time. Not a prompting problem.
2. A fabricated telemetry column is worse than an absent one, because downstream consumers
   (the histogram, the next run's entry rungs) treat it as measurement.
3. Whatever writes the row must be a shell command, since that is the only participant in a
   baton run with access to a clock.
4. The fix must survive resume, because a session limit landing mid-run is an expected event,
   not an exception.

## Recommended Approach

**Move the append to envelope-receipt, and persist the start time on disk.**

**1. Split the row into two writes, or move it to one.** The phase runner knows dispatch time
in-turn and receipt time in-turn. Preferred: write the row **once, at envelope receipt**, when
`verdict` and `seconds` are both real. Amend `phase-runner.md` step 3 accordingly.

**2. Persist the dispatch time on disk — written by the phase runner, not the child.**

The obvious move is to have the child stamp `started_at` into `status.json`. **It cannot.**
`prompt/CONTRACT.md:549` (§11, appended verbatim to every spawn) reads *"As your **final act**
write `{status_path}` matching the envelope schema exactly."* The envelope is written once, at
the end. Writing it twice would break both "the envelope is your entire interface" and §2's
"disk copy wins on conflict" rule.

The phase runner is the right writer anyway: it already shells out at dispatch to append the
ledger row, and it is the only layer alive on **both** sides of the child's life. So at dispatch
it writes `_orch/nodes/<id>/started_at` (one line, `date -u +%FT%TZ`), and at envelope receipt it
reads that file back, subtracts, and appends the completed row. Add `started_at` to §6's
filesystem listing.

Resume-safe by construction: a phase runner respawned mid-phase reads the file like every other
piece of run state, which is what premise 4 requires.

**3. Mandate shell-stamped fields in §7.** `ts` and `seconds` come from `date -u +%FT%TZ` and a
subtraction against `started_at` **in the append command itself** — never from the model's account
of how long it took. Add the required command shape to §7 so there is no ambiguity about who holds
the clock.

**4. Make fabrication detectable.** A verifier can compare the ledger's first and last `ts`
against the operator-observed wall-clock span. Cheap, and it is the only check that catches a
regression here.

## Alternatives Considered

- **Drop `seconds` and `ts` from the schema.** Honest, and strictly better than fabricating them.
  Rejected because the histogram is the product's central feedback loop; removing the input
  removes the loop.
- **Have the prime stamp rows.** The prime is also a model. Same defect, moved.

## Open Questions

- Does a token/cost column belong beside `seconds`? The README's pitch is cost discipline, and
  seconds is a proxy. Out of scope here, but the schema change is the moment to decide.
- Should a run with fabricated-looking timestamps fail its gate, or just warn?

## Success Criteria

- `ledger.csv` from a real run has `ts` values matching operator-observed wall clock **within 60
  seconds**, and a `seconds` column whose sum is within 10% of the run's observed duration.
- Every row has a `verdict` that is a fact, not a prediction.
- A run interrupted by a session limit and resumed produces correct `seconds` for nodes that
  spanned the interruption.

## Next Steps

2. Add `_orch/nodes/<id>/started_at` to §6's filesystem listing in `prompt/CONTRACT.md`, written

   final-act, write-once file.
3. Amend §7 with the required shell-stamped append shape.
4. Run any mode end to end and check the ledger against a stopwatch.

## Why This Ships First

It is roughly a ten-line change across three files, it has an independent success criterion, and
it is not blocked by the persona work in `stage-aware-luminaries.md`. It also makes the receipt
real for that design's validation runs, which is the only way those runs can demonstrate anything
about cost.
